微信小程序项目规格说明书
项目名

英语句子复习小程序

1. 项目目标

为用户提供一个极简的英语听力复习工具。

核心场景：

用户每天打开小程序
页面展示当天需要复习的若干句子 card
每个 card 可以点击播放对应句子音频
当前阶段先不做复杂 SRS
当前规则先简化为：每天随机抽取 3 句话
2. MVP 范围
2.1 本期必须实现

只有一个页面，包含以下能力：

展示“今日复习句子”列表
每条句子显示为一个 card
每个 card 有一个播放按钮
点击后播放这一句对应的音频片段
每天固定抽取 3 句
当天内多次打开，抽到的 3 句保持一致
第二天重新随机抽取
2.2 本期不做

这些都先不做，避免项目膨胀：

登录系统
云端同步
账号体系
多本书管理
逐句录音
跟读评分
真正的 Anki / SRS 算法
中文显示/隐藏切换
收藏、错题本
后台管理页面
自动切音频功能
3. 用户画像
主要用户

用户母亲，英语初学者或非常初级学习者。

用户特征
不适合复杂操作
不适合复杂 UI
只需要打开就能用
对“每天一句/几句”这种固定节奏更容易坚持
4. 核心设计原则
4.1 极简

一个页面即可，不做多级导航。

4.2 低认知负担

用户不需要理解“导入、标签、复习算法”等概念。

4.3 快速反馈

点击就能播放，不做额外确认。

4.4 工程简单

先使用：

一个完整音频文件或一个段落音频文件
若干句子的 start/end 时间戳
前端本地存储每日抽取结果
5. 功能规格
5.1 页面：今日复习页
页面目标

展示当天待复习的 3 句话。

页面元素

每个 card 包含：

句子英文文本
播放按钮
播放中状态

页面顶部包含：

标题：今日复习
可选按钮：重新抽取（开发调试用，可后续下线）

页面底部包含：

停止播放按钮（可选，但建议有）
5.2 每日抽取逻辑
规则
从所有句子中随机抽取 3 句
同一天内固定不变
第二天重新抽取
存储方式

使用小程序本地存储保存：

当天日期
对应抽中的句子 ID 列表
示例
{
  "date": "2026-04-12",
  "sentenceIds": [3, 18, 27]
}
5.3 播放逻辑
输入

每条句子具备：

audioUrl
start
end
行为

用户点击“播放”后：

若当前已有音频在播，先停止
将音频 seek 到 start
开始播放
到达 end 时自动暂停
UI 显示当前 card 为“播放中”
约束
页面内只允许同时存在一个音频实例
不为每个 card 单独创建播放器
5.4 音频资源策略
当前建议方案

不要做“每句一个 mp3 文件”。

使用：

一个段落级 mp3
每句对应 start/end
原因

这样最省事：

文件数量少
管理简单
不需要导入几百个文件
前端逻辑足够满足 MVP
6. 数据模型
6.1 句子数据结构
type Sentence = {
  id: number;
  en: string;
  zh?: string;
  audioUrl: string;
  start: number;
  end: number;
};
字段说明
id: 唯一 ID
en: 英文句子
zh: 中文，可选，MVP 可不展示
audioUrl: 音频地址
start: 开始时间，单位秒
end: 结束时间，单位秒
6.2 每日复习数据结构
type DailyReview = {
  date: string;
  sentenceIds: number[];
};
6.3 本地存储 key 设计
review_cards_YYYY-MM-DD

例如：

review_cards_2026-04-12
7. 技术方案
7.1 技术栈
前端
微信小程序原生

数据源

7.2 为什么不用后端

当前 MVP 没必要上后端。

因为当前需求只有：

固定句子数据
每天随机抽取
本地持久化

这些都可以纯前端完成。

8. 页面交互规格
8.1 页面初始加载

页面打开时：

创建唯一音频实例
检查本地是否已有当天抽取结果
如果有，直接读取
如果没有，随机抽取 3 句并缓存
渲染 card 列表
8.2 点击播放按钮
正常流程
找到句子数据
停止当前音频
设置 playingId
seek(start)
play()
到 end 后自动暂停并清空 playingId
异常处理

若播放失败：

toast 显示“播放失败”
清空播放状态
8.3 切换播放句子

如果用户在 A 句播放过程中点击 B 句：

停止 A
清理旧定时器
播放 B
8.4 页面销毁

页面关闭或切走时：

停止音频
清除定时器
销毁音频实例
9. 非功能需求
9.1 性能要求
页面加载
首屏尽量在 1 秒内展示出 card 文本
音频允许延迟缓冲，但 UI 不应卡死
音频
复用单个音频实例
避免重复创建播放器造成资源浪费
9.2 可维护性
句子数据和页面逻辑分离
音频控制逻辑集中管理
每个函数职责单一
9.3 可扩展性

后续可扩展为：

显示中文
会了/不会按钮
复习算法升级
多音频分段
云同步

所以当前数据结构不要写死得太糟糕。

负责生成当天日期 key

示例：

export function getTodayKey() {
  const d = new Date();
  const y = d.getFullYear();
  const m = String(d.getMonth() + 1).padStart(2, '0');
  const day = String(d.getDate()).padStart(2, '0');
  return `${y}-${m}-${day}`;
}

12. 音频切分策略建议
当前推荐

不要整本书只放一个超长 mp3。

更好的方案是：

按段落或章节拆成多个较小音频文件
每个句子只记录自己所在段落文件的 audioUrl + start/end
原因

如果一个 mp3 太长：

seek 体验更差
首次缓冲更慢
随机跳句更容易 waiting
推荐粒度

每个音频文件控制在：

1～3 分钟最佳
最多不超过 5 分钟
13. 错误与边界情况
13.1 音频地址失效

行为：

toast 显示“音频加载失败”
不崩溃
13.2 时间戳异常

比如：

start >= end
end 超出音频长度

行为：

不播放
console 报错
可 toast “数据异常”
13.3 句子总数不足 3

行为：

有几句就展示几句
不强制补齐
13.4 当天缓存损坏

行为：

删除缓存
重新随机抽取

16. 开发顺序建议

按这个顺序做最稳：

第一步

静态页面先出来
只渲染 3 个假数据 card

第二步

接音频播放
先拿一个固定句子测通 seek + play + pause

第三步

接随机抽取逻辑
做当天缓存

第四步

把真实句子数据接进去

第五步

补异常处理和 UI 状态

17. 关键实现决策
决策 1：单页应用

理由：需求极简，避免复杂导航

决策 2：一个音频实例

理由：避免资源浪费和并发播放

决策 3：本地缓存每日句子

理由：不需要后端即可满足“每日固定”

决策 4：一个段落音频 + 时间戳

理由：比“每句一个文件”更省维护成本

18. 风险与应对
风险 1：长音频 seek 体验不好

应对：

按段落拆 mp3
不用整本单文件
风险 2：手工时间戳成本高

应对：

先只标前 20 句
够用再扩
风险 3：需求膨胀

应对：

严格只做单页 + 3 句 + 播放
19. MVP 成功定义

这个项目不是要做成“完整英语平台”，而是：

让用户每天能无障碍地点开、点一句、听一句，并且能持续用下去。

如果你妈能连续用一周，而且不需要你天天教她怎么操作，
这个 MVP 就算成功。
